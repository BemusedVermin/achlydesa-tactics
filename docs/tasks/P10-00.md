# P10-00 — Plan Phase 10: Movement III

**Agent:** spec-writer · **Size:** M · **Depends on:** G9 · **Branch slug:** plan-phase-10 · **Runs on:** either

## Goal
Write the complete set of task specs for Phase 10 (Movement III), so that every task in the phase can be handed to an agent and reviewed against runnable acceptance criteria. The specs are built from what actually exists in the code and what the previous phases' reviews and gates taught, not from what the roadmap guessed.

## Read first
- `docs/ROADMAP.md` §How phases become tasks and §Phase 10.
- `docs/tasks/TEMPLATE.md`, and two exemplar specs: `docs/tasks/P1-11.md` (a large simulation task) and `docs/tasks/P1-13.md` (a library with binding formats).
- The design sections listed under §Phase 10 *Implements*. Read only those.
- What actually exists:
  - the public APIs of the crates the phase touches (`grep -rn "^pub " crates/<crate>/src`);
  - merged PRs from the previous phase (`gh pr list --state merged --limit 100`), especially their Deviations and Open questions sections;
  - all comments on the previous gate's issue (`python tools/scripts/gh_task.py comments G9`).
- Accepted ADRs in `docs/decisions/`.

## Deliverables
- `docs/tasks/P10-01.md`, `P10-02.md`, …: one spec per task, plus spikes as `P10-S1.md` and so on.
- `docs/tasks/H10-1.md`, …: human decision steps, only if needed (see Specification).
- `docs/decisions/ADR-*.md` (Status: Proposed): one per decision that needs Liam.
- `docs/tasks/G10.md`: update *Depends on* to the phase's final tasks; refine the steps if the built scenario names changed.
- `docs/tasks/README.md`: index rows for every new spec, in execution order, and the dependency graph.
- `docs/ROADMAP.md`: §Phase 10 only. Record the decisions taken and set the section's first line to `**Specified:** <date>, by P10-00`.

## Specification
1. **Decide before specs.** For each item in the roadmap's *Decide before specs* list:
   - if existing canon or an Accepted ADR settles it, cite that;
   - otherwise write a Proposed ADR with options and a recommendation, add a human step `H10-k — Decide ADR-NNNN` (Agent: Liam, Runs on: human), and make every dependent task depend on it.
2. **Granularity.** Each task is S, M, or L and completable in one agent session. Split anything XL. Prefer one crate (plus its tests and content) per task. Public interfaces get their own task when other tasks depend on them.
3. **Spec quality.** Follow `TEMPLATE.md` exactly, including the header line: Agent, Size, Depends on, Branch slug, Runs on.
   - *Read first* names exact sections.
   - *Deliverables* is exhaustive.
   - *Specification* gives binding Rust signatures for public APIs, data formats, and algorithms with their integer arithmetic.
   - *Acceptance* contains runnable commands and checkable properties.
   - *Out of scope* blocks the obvious over-reach.
   - *Review focus* tells Liam where to look hardest.
4. **Runs on.** Use `local` when a task needs the raw terrain tiles, a GPU or display, or Liam's eyes on a running build. Otherwise use `either`.
5. **Feeling.** Every Goal states which of awe, despair, hope, or fun the task serves, or says plainly that it is plumbing. The phase's feeling gate must be reachable from the built tasks.
6. **Determinism and boundaries.** Every simulation-side spec restates the CLAUDE.md rules it touches. Any new crate edge appears in a task that edits `xtask/allowed_deps.toml`, with justification.
7. **Do not** write specs for Phase 11, edit design documents, or decide anything that belongs in an ADR.

## Acceptance
- `python tools/scripts/gh_task.py specs --check` exits 0. It checks that every spec parses, every dependency exists, there are no cycles, and every required section is present.
- Every roadmap candidate task is either specified, merged into another spec (say which), or dropped with a reason in the PR description.
- `git diff --stat` touches only the deliverables above.

## Out of scope
Implementing anything. Specs for later phases.

## Review focus (Liam)
The dependency graph, the interface tasks, and the proposed ADRs. Fixing a spec costs minutes; fixing code built on a bad spec costs days.
